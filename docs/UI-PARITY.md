# UI 一致性（原型 ↔ 真实界面）

日期：2026-10-17 · 产物版本 v0.2.0。检查命令：`npm run check:ui-parity`。

## 1. 为什么用"比对"而不是"看着像"

界面是从 `prototypes/v0.1` 派生的：同一份 `style.css`、同一套渲染函数。派生代码最容易出的
问题不是崩，而是**有人顺手改了文案、删了一个提示条、换了一种着色**——单个改动都看不出，
累积起来就不再是签认过的那个界面。DEV-PLAN §4 第 3 条把"UI 以确认后的原型为准"写成了硬约束，
所以需要一条能跑的尺子，而不是靠记忆。

## 2. 量什么

| 指标 | 算法 | 性质 |
| --- | --- | --- |
| **结构一致率**（主指标） | 遍历 `#main` 内所有元素，取 `标签 + 类名 + display + 字号` 组成序列，两边做 LCS，得分 = 2·LCS / (len_a + len_b) | 反映布局、层级、样式是否变了 |
| **文本一致率**（参考） | `innerText` 按行去重后同样做 LCS | 数据源换了会掉，属预期，单独列出 |
| 附带检查 | 每个视图的 JS 异常、页面级横向溢出（`scrollWidth - clientWidth`） | 有任一异常即判失败 |

判定：结构一致率**均值 ≥ 98%**，且无 JS 异常、无页面级横向溢出。单视图低于 98% 会打印出来，
由人判断是不是"数据源变了"导致的。

脚本：`scripts/check-ui-parity.mjs`。它自己起一个本机服务（端口 8789）与一台无头 Chrome
（CDP 9335），逐视图在两边设同一个 hash 再抽取 DOM。不进 `npm run check`，因为依赖本机 Chrome。

```
npm run check:ui-parity                                  # 默认 1440px
node --disable-warning=ExperimentalWarning scripts/check-ui-parity.mjs --widths=936,1440,390
```

## 4. 已知差异（都是刻意的，逐条有理由）

| 视图 | 差异 | 为什么 |
| --- | --- | --- |
| `#trials` 结构 97.8% · 文本 55.6% | 节点数相同（46→46），差 1 个 pill 的着色；文本换成真实登记数据 | 原型写的是「示例登记号 A/B/C」。真实界面读知识库 `trial` 表，标题/登记号/状态都是真实登记内容——**这是本次系统化的目的**。着色按状态文案里是否含"招募"判定，ChiCTR 快照没有状态字段，如实显示"状态见登记原文" |
| `#timeline` 结构 99.2% | 多了一个「治疗毒性」分类组（0 项）和一个「基线 PET」节点 | 分类组来自 `metric_def`：CTCAE 是分类变量（`is_numeric = 0`），留在分组里正是为了在界面上写清"它不能画趋势"（A11）。评估节点来自 `response` 表，基线也是一次评估，不该漏 |
| 顶栏「对话」 | 原型"未进入激活"，界面"未接入" | 会话能力在 M5 才接；不写"未进入激活"是避免暗示它已经存在 |
| 设置面板 | 多了「临床数据库」tab（亚型数 / 试验条数 / 年份口径） | 本次接入了知识库，得让用户看得见它接的是什么、口径是什么 |
| 全局 | 原型顶部的演示条 `.prototype-bar` 不渲染 | 真实界面不需要"全部为模拟资料"的免责条——资料是真的 |

## 5. 什么情况下该改这条线

- 原型改了界面（G2 之后仍有改动）→ 重跑本脚本，一致率应回到 98% 以上；
- 界面为了修 bug 改了结构 → 若一致率掉到 98% 以下，要么改回原型的结构，要么回到 G2 讨论；
- **数据源变化导致的文本下降不拦**（例如试验换成真实登记），但要在本文件第 4 节登记理由。
